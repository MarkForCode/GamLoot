執行重構優化工作流程。重構目標：$ARGUMENTS

## 工作流程

### 1. 理解現狀
- 若 $ARGUMENTS 未說明範圍，詢問要重構哪個部分以及原因
- 確認重構動機：效能 / 維護性 / 可讀性 / 技術債
- 讀取相關程式碼，理解現有邏輯
- 列出受影響的檔案清單

### 2. 規劃
- 評估重構複雜度
- 確認重構後的目標狀態
- 確認現有測試覆蓋範圍（避免重構破壞未測試的行為）
- 規劃小步驟：每次只動一個部分

若重構複雜，**先說明計畫，等待用戶確認再執行**。

### 3. 執行重構（小步前進）
- 先確認現有功能正常（執行一次 lint / build）
- 每次只改一個小部分
- 保持功能行為不變（除非用戶明確要求改變）
- 每個小步驟後驗證不破壞現有功能

### 4. 驗證
- 執行 `pnpm lint` 或 `just lint`
- TypeScript typecheck
- 執行 `pnpm build`
- 手動測試核心功能正常

### 5. 完成報告
- 說明改動了什麼、為什麼這樣改
- 討論後續還可以優化的地方（但不要過度延伸）

## 重構類型參考

| 類型 | 常見操作 |
|------|---------|
| 程式碼風格 | 改命名、格式化、遵循 convention |
| 架構重構 | 拆分大檔案、建立共享模組、改善 module 依賴 |
| 效能優化 | 優化 DB 查詢、加快取、減少不必要計算 |
| 技術債 | 移除 dead code、補齊 TypeScript 型別、更新依賴 |

## 重要原則
- **小步前進**：每次只改一點，避免一次大改壞掉
- **保持功能**：重構不等於改行為，除非明確說要改
- **頻繁驗證**：改了之後馬上跑 lint / build
- **有疑問就問**：不確定的設計選擇先確認再動手

## Commit 訊息格式
```
refactor(scope): 簡短描述

- 具體改動 1
- 具體改動 2
- No behavior change（若行為未改變）
```
