執行 Bug 修復工作流程。問題描述：$ARGUMENTS

## 工作流程

### 1. 收集資訊
- 若 $ARGUMENTS 未提供足夠細節，詢問：
  - 錯誤訊息或截圖
  - 觸發情境（什麼操作導致）
  - 環境（dev/prod、瀏覽器/手機/API）
  - 是否有 logs（`docker compose logs`、`just docker-logs`）

### 2. 重現問題
- 嘗試在本地重現 bug
- 讀取 `logs/` 目錄或執行 `just docker-logs` 查看相關 log
- 確認觸發條件與頻率（每次 / 偶爾 / 特定條件）

### 3. 分析 Root Cause
- 定位問題在前端 / 後端 / 資料庫
- 讀取相關程式碼，找出根本原因
- 不要只看表面錯誤，要追蹤到真正的問題來源

### 4. 修復
- 撰寫修復程式碼
- 確保不引入新 bug
- 保持現有功能正常運作
- 複雜的 bug 修復前先說明修復方案，等待確認

### 5. 驗證
- 本地測試確認修復有效
- 執行 `pnpm lint` / typecheck / `pnpm build`
- 確認相關功能沒有被影響

### 6. 修復報告
輸出以下格式：

```
## Bug 修復報告

**問題**: [簡述現象]
**原因**: [root cause]
**修復**: [做了什麼修改]
**驗證**: [測試結果]
```

## 緊急修復 (Hotfix)
若用戶說「很緊急」或「系統掛了」：
1. 立即重現問題
2. 快速找到可行解（不必完美）
3. 先修復上線，後續再優化
4. 修復後補充完整的 root cause 分析

## 修復原則
- 找根本原因，不修表面症狀
- 不確定修法時，先說明方案再動手
- 小心不要製造新的 bug
